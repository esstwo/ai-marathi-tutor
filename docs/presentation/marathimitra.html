The problem

Diaspora kids understand Marathi — but freeze when it's time to speak.

  • They hear it at home, but reply in English
  • Lose confidence; the gap widens with age
  • Traditional apps (Duolingo-style) are great for vocab, terrible for spoken practice
  • 1:1 tutors cost ₹500–1500/hour, can't be on-demand at bedtime
  • Parents juggle full-time work; they can't run Marathi lessons every evening
Result: a whole generation of kids who can understand their mother tongue but can't comfortably speak it.

The key idea: Skills + Connectors

Old way: business logic + AI prompts buried in Python service code.

New way:

  • Skills = portable Markdown files. System prompt + YAML metadata (inputs, outputs, connector deps). The skill is the intelligence.
  • Connectors = tiny Python functions that touch external systems. Zero business logic.
  • Gateway = thin HTTP layer that loads a skill, hands it connectors, runs a generic agentic loop.
Adding a new capability = writing a new .md file. No Python plumbing.

Same skill files run in the web app, in Claude Desktop (via MCP), or in any future client.

LLM as orchestrator

Instead of the backend orchestrating the LLM…

# OLD: backend knows what context it needs
profile = fetch_profile(child_id)
lesson = fetch_lesson(level)
response = call_llm(prompt, profile, lesson)

…the LLM orchestrates the backend.

# NEW: LLM gets connector tools and decides what it needs
result = run_skill(conversation_skill, messages, connectors={
    "get_child_profile": ...,
    "get_lesson_context": ...,
})

Tool schemas auto-generated from Python signatures. Backend logic shrinks; intelligence grows.

Sarvam: three sharp design choices

1. No vendor SDK lock-in. Sarvam exposes an OpenAI-compatible API, so we use the openai Python SDK pointed at api.sarvam.ai/v1. Future provider swap = one base-URL change.

2. Three-layer JSON enforcement. Sarvam doesn't support response_format, so we enforce JSON via:

  • Strict "Output format" sections at the top of each skill prompt
  • [Reply as JSON object: {...}] reminder appended to every user turn (not saved to history — chat UI stays clean)
  • Defensive parse_json_response — strips markdown fences, extracts first {...} substring, then falls back to plain text

3. Pre-fetch context instead of tool-calling. The gateway already has child + mission data; making the LLM call tools to re-fetch was overhead. Now injected directly into the system prompt — 1 LLM round per turn instead of 3–4, no empty-response failures.

Production-ready: cost & abuse hardening

Before opening signups publicly:

  • Per-child daily LLM cap — persisted in Supabase via atomic Postgres RPC, defaults to 100 calls/day. One abusive account can't burn the global budget.
  • Per-IP signup rate limit — persisted, X-Forwarded-For aware, blocks bots even before they touch Supabase Auth.
  • Cloudflare Turnstile on both signup AND login — verified server-side by Supabase.
  • Email verification before login + branded Resend templates for verification / reset / digest.
  • CORS that doesn't lie — env parser tolerates whitespace, logs parsed allowlist at startup.
  • 123 pytest cases covering every guardrail surface.
